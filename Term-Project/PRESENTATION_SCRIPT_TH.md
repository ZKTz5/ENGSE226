# บทนำเสนอ ENGSE226: RMUTL Shuttle Booking System

**ระยะเวลาเป้าหมาย: 7–10 นาที**  
**หมายเหตุ:** ข้อความในวงเล็บเหลี่ยมเป็นคำแนะนำสำหรับผู้พูด ไม่ต้องอ่านออกเสียง

## 1. เปิดการนำเสนอ — ประมาณ 45 วินาที

สวัสดีครับ/ค่ะ อาจารย์และเพื่อน ๆ วันนี้กลุ่มของเราจะนำเสนอโปรเจกต์ **RMUTL Shuttle Booking System** ซึ่งเป็นระบบค้นหาและจองรถรับส่งระหว่างวิทยาเขตของมหาวิทยาลัยเทคโนโลยีราชมงคลล้านนา

โปรเจกต์นี้เริ่มต้นจาก Campus Service เดิม แล้วปรับส่วนการใช้งานหลักให้รองรับการค้นหาตารางรถ การจองที่นั่ง และการจัดการคิวสำรอง โดยยังคงใช้โครงสร้างหลักของระบบเดิม ได้แก่ Express สำหรับ API, SQLite สำหรับฐานข้อมูล และ React กับ Vite สำหรับส่วนติดต่อผู้ใช้

## 2. ปัญหาและเป้าหมาย — ประมาณ 50 วินาที

ผู้ใช้ที่ต้องเดินทางระหว่างวิทยาเขตควรตรวจสอบได้ว่ามีรถออกจากที่ใด ไปที่ใด และออกเดินทางเมื่อไร ระบบนี้รองรับจุดให้บริการสองแห่ง คือเจ็ดยอดและดอยสะเก็ด โดยให้บริการเดินทางได้ทั้งสองทิศทาง ผู้ใช้ค้นหาตามต้นทาง ปลายทาง และวันที่เดินทาง จากนั้นดูจำนวนที่นั่งและจองได้

ถ้าที่นั่งเต็ม ระบบรับคำขอเข้า waitlist และเมื่อมีผู้ยกเลิกที่นั่ง ระบบจะเลื่อนผู้โดยสารคนถัดไปตามลำดับคิว เป้าหมายคือให้ข้อมูลที่ผู้ใช้เห็นสอดคล้องกับผลการจองที่ backend เป็นผู้ตรวจสอบ

## 3. Sprint 1: ฐานข้อมูลและการเข้าสู่ระบบ — ประมาณ 1 นาที

Sprint แรกเตรียมตารางหลักสำหรับผู้ใช้ วิทยาเขต ตารางรถ และการจอง พร้อมข้อมูลตั้งต้นสำหรับการทดลองใช้งาน

ระบบเข้าสู่ระบบด้วยอีเมลที่ลงท้ายด้วย `@live.rmutl.ac.th` ตรวจสอบฟิลด์ที่จำเป็นและข้อมูลรับรอง จากนั้นออก JWT ให้ frontend ส่งเป็น Bearer token เมื่อเรียก endpoint ที่ต้องเข้าสู่ระบบ รหัสผ่านจัดเก็บในรูปแบบ hash ด้วย scrypt

อีกส่วนหนึ่งคือการป้องกันฐานข้อมูลเก่าจาก Campus Service หาก schema ไม่ตรงกับระบบ Shuttle ตัวระบบจะแจ้งปัญหาและไม่ reset ข้อมูลโดยอัตโนมัติ ผู้ดูแลต้องสำรองข้อมูลแล้วเลือก migrate หรือ reset อย่างชัดเจน

## 4. Sprint 2: วิทยาเขตและตารางรถ — ประมาณ 1 นาที

Sprint ที่สองเพิ่มข้อมูลสามวิทยาเขตและ API สำหรับดูวิทยาเขตกับตารางรถ ผู้ใช้เลือกต้นทาง ปลายทาง และวันที่เดินทางได้ ส่วน backend ตรวจสอบรูปแบบ filter และปฏิเสธกรณีที่ต้นทางกับปลายทางเป็นวิทยาเขตเดียวกัน

ข้อมูลตารางรถประกอบด้วยเส้นทาง เวลาออก ความจุ จำนวนที่นั่งที่ยืนยันแล้ว จำนวนที่นั่งว่าง และสถานะ สถานะหมดอายุพิจารณาจากเวลาออกเดินทางจริง ไม่ได้อาศัยค่า active ที่บันทึกไว้เพียงอย่างเดียว และ backend ปฏิเสธการจองหลังเวลาเดินทางแล้ว

## 5. Sprint 3: การจองและ waitlist — ประมาณ 1 นาที 20 วินาที

Sprint ที่สามเพิ่มการจอง การยกเลิก และ waitlist ผู้ใช้ที่เข้าสู่ระบบแล้วจองตารางรถได้หนึ่งรายการต่อหนึ่งผู้ใช้และหนึ่งเที่ยว หากที่นั่งหมด คำขอจะถูกเพิ่มเป็น waitlisted และผู้ใช้สามารถดูรายการของตนเองหรือยกเลิกได้

การเปลี่ยนแปลงจำนวนที่นั่งทำใน immediate transaction ของ SQLite เพื่อจัดลำดับการเขียนและป้องกันการรับจองเกินจำนวนที่นั่งในการทำงานแบบ local เมื่อยกเลิก booking ที่ยืนยันแล้ว ระบบจะเลือกผู้รอคิวที่มี `created_at` เก่าที่สุด ถ้าเวลาเท่ากันจะใช้ booking ID เป็นตัวตัดสิน การยกเลิกและการเลื่อนคิวเกิดใน transaction เดียวกัน ส่วนการยกเลิกรายการ waitlist จะไม่ทำให้มีการเลื่อนคนอื่น

เราเพิ่ม integration test กรณีผู้ใช้หลายคนแย่งที่นั่งสุดท้าย รวมถึงทดสอบลำดับ FIFO เมื่อเวลาสร้างตรงกันด้วย ข้อสรุปเรื่อง concurrency นี้ยืนยันเฉพาะ SQLite ที่ใช้ทดสอบในเครื่อง ยังไม่ได้ยืนยันกับฐานข้อมูล remote

## 6. Sprint 4: ส่วนติดต่อผู้ใช้ — ประมาณ 1 นาที

Sprint สุดท้ายปรับ active user flow เป็นหน้าล็อกอิน แดชบอร์ด หน้าค้นหาและรายการตารางรถ หน้ารายละเอียดเที่ยวรถ และหน้า My Bookings

ผู้ใช้เห็นสถานะกำลังโหลด ไม่มีผลลัพธ์ หรือเกิดข้อผิดพลาด รวมถึงผลการจองแบบ confirmed หรือ waitlisted และสถานะเต็มหรือหมดอายุ หน้าจอใช้ข้อมูลจริงจาก API และมี CSS สำหรับหน้าจอ desktop และ mobile

ขณะนี้ token อยู่ในหน่วยความจำของแอป เมื่อ reload หน้า ผู้ใช้จึงต้องเข้าสู่ระบบใหม่

## 7. สาธิตระบบ — ประมาณ 2–3 นาที

[เปิดหน้า Dashboard]

นี่คือแดชบอร์ด ระบบโหลดเที่ยวรถจาก API และแสดงรายการเดินทางที่กำลังจะมาถึง

[เปิด Schedules เลือกต้นทาง ปลายทาง และวันที่ แล้วกดค้นหา]

หน้านี้ค้นหาตารางรถด้วยต้นทาง ปลายทาง และวันที่ ข้อมูลผลลัพธ์มาจาก backend โดยตรง ถ้าเลือกต้นทางและปลายทางเหมือนกัน ระบบจะแจ้งว่า filter ไม่ถูกต้อง

[เปิด Schedule Detail]

ในรายละเอียดเราเห็นเส้นทาง เวลาออก ความจุ จำนวนที่นั่งที่ยืนยันแล้ว ที่นั่งว่าง และสถานะของเที่ยวรถ หากเที่ยวรถหมดเวลาแล้ว จะไม่สามารถกดจองได้

[เข้าสู่ระบบด้วยบัญชีตัวอย่างและรหัสผ่านสำหรับ demo จาก audit report]

บัญชีนี้เป็นบัญชี seed สำหรับการทดสอบเท่านั้น ไม่ใช่ข้อมูลสำหรับ production หลังเข้าสู่ระบบ frontend จะส่ง JWT ไปกับคำขอจอง

[จองเที่ยวรถที่ยังมีที่นั่ง แล้วเปิด My Bookings]

การจองสำเร็จจะแสดงสถานะ confirmed และรายการจะปรากฏใน My Bookings จากตรงนี้ผู้ใช้ยกเลิกการจองได้

[ถ้าเตรียมฐานข้อมูล demo แบบ disposable ที่มีเที่ยวรถ capacity เท่ากับหนึ่ง ให้แสดงการจองด้วยบัญชีสองบัญชีและการเลื่อน waitlist; มิฉะนั้นอธิบายผลจาก integration test]

เมื่อที่นั่งเต็ม ผู้ใช้ลำดับถัดไปจะได้สถานะ waitlisted เมื่อยกเลิกผู้ที่ confirmed ระบบเลื่อนผู้รอคิวคนแรกขึ้นมา การทดสอบ backend ตรวจกรณีนี้ รวมถึงกรณีเวลาสร้างซ้ำกัน

## 8. การทดสอบและข้อจำกัด — ประมาณ 1 นาที

ผลการตรวจล่าสุดที่บันทึกไว้คือ backend ผ่าน 44 tests จาก 7 ไฟล์ และ frontend ผ่าน 7 tests จาก 2 ไฟล์ คำสั่ง production build ผ่านเช่นกัน การทดสอบครอบคลุมการเข้าสู่ระบบ การกรองตารางรถ เวลาเดินทางหมดอายุ การจองซ้ำ การยกเลิก การเป็นเจ้าของรายการ FIFO และการแย่งที่นั่งพร้อมกันใน SQLite

ข้อจำกัดสำคัญคือ Render blueprint ปัจจุบันใช้ SQLite บน free plan ซึ่งเป็น storage แบบ ephemeral จึงยังไม่ควรใช้เก็บ booking จริงระยะยาว ต้องเลือกและกำหนด persistent storage ก่อน และยังไม่มีการ deploy production หรือทดสอบ transaction กับฐานข้อมูล remote

## 9. สรุป — ประมาณ 30 วินาที

สรุปแล้ว ระบบปัจจุบันครอบคลุมฟังก์ชัน Sprint 1 ถึง Sprint 4 สำหรับการเข้าสู่ระบบ ค้นหาตารางรถ จอง ยกเลิก และเลื่อน waitlist พร้อมผลทดสอบและ build ที่ผ่านในสภาพแวดล้อมปัจจุบัน งานก่อนใช้งานจริงคือกำหนดฐานข้อมูลถาวร ทดสอบการ deploy และยืนยันพฤติกรรม transaction กับ storage ที่เลือก

ขอบคุณครับ/ค่ะ ยินดีตอบคำถามครับ/ค่ะ

## เช็กลิสต์ก่อนนำเสนอ

- ทดลองเปิด API และ frontend ในเครื่องก่อนวันนำเสนอ
- เตรียมบัญชี seed สำหรับ demo และตรวจว่ารหัสผ่านตัวอย่างยังใช้ได้ในฐานข้อมูล demo
- ใช้ฐานข้อมูลที่ reset ได้เมื่อสาธิตการจอง การยกเลิก หรือการเลื่อน waitlist
- หากวันเดินทางใน seed data ทำให้สถานะ expired เปลี่ยนไปตามเวลา ให้เตรียมฐานข้อมูล demo ให้เหมาะสมล่วงหน้า
- อย่านำเสนอว่ามี production deployment หรือ remote database concurrency ที่ผ่านการตรวจแล้ว
