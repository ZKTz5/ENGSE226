# บทนำเสนอ ENGSE226: RMUTL Shuttle Vehicle Request System

**ระยะเวลาเป้าหมาย: 7–10 นาที**

## 1. เปิดการนำเสนอ — 45 วินาที

สวัสดีครับ/ค่ะ วันนี้กลุ่มของเราจะนำเสนอ RMUTL Shuttle ระบบรับคำขอใช้รถระหว่างเจ็ดยอดและดอยสะเก็ด โดยรถมีฐานประจำที่เจ็ดยอด ผู้ใช้ระบุวันและเวลาที่ต้องการเดินทาง แล้วส่งคำขอให้เจ้าหน้าที่ตรวจสอบ

ระบบยังใช้ React กับ Vite, Express, SQLite, JWT และ scrypt ตามสถาปัตยกรรมเดิม แต่ business flow เปลี่ยนจากการเลือกเที่ยวรถที่กำหนดไว้ เป็นการส่งคำขอใช้รถ

## 2. ปัญหาและขอบเขต — 50 วินาที

รถไม่ได้วิ่งตามตารางประจำอย่างต่อเนื่อง ผู้ใช้จึงต้องแจ้งความต้องการเดินทางล่วงหน้า ระบบรองรับเพียงสองจุดคือเจ็ดยอดและดอยสะเก็ด ต้นทางกับปลายทางต้องต่างกัน และผู้ใช้เลือกได้ทั้งเที่ยวเดียวกับไป-กลับ

การกดส่งหมายถึงระบบรับคำขอเข้าสู่สถานะ `PENDING` เท่านั้น ยังไม่ได้อนุมัติให้ใช้รถ ไม่มีการเลือกที่นั่ง ไม่มี waitlist และระบบไม่ได้ติดตาม GPS

## 3. Sprint 1: Database และ Authentication — 1 นาที

ฐานข้อมูลปัจจุบันมี users, vehicles และ vehicle_requests. ผู้ใช้เข้าสู่ระบบด้วยอีเมลที่ลงท้ายตรงตัวด้วย `@live.rmutl.ac.th` โดยไม่แยกตัวพิมพ์เล็ก/ใหญ่ Backend ตรวจรหัสผ่านด้วย scrypt และออก JWT เพื่อใช้กับ endpoint ที่ต้องยืนยันตัวตน

ระบบไม่มีหน้าสมัครหรือ public self-signup. บัญชี seed ใช้สำหรับ demo; การสร้างบัญชีจริงเป็นหน้าที่ผู้ดูแลระบบ

## 4. Sprint 2: Vehicle Request — 1 นาที

แบบฟอร์มรับรูปแบบการเดินทาง ต้นทาง ปลายทาง วันที่และเวลา จำนวนผู้โดยสาร วัตถุประสงค์ และหมายเหตุ ผู้ใช้ตรวจทานข้อมูลก่อนกดยืนยันส่ง คำขอไป-กลับต้องระบุเวลากลับ ส่วนเที่ยวเดียวสามารถระบุเวลาสิ้นสุดภารกิจได้

Backend ตรวจสถานที่ เวลาอนาคต จำนวนผู้โดยสาร และข้อมูลที่จำเป็นอีกครั้ง โดยไม่เชื่อ status หรือ vehicle assignment ที่ส่งมาจาก browser

## 5. Sprint 3: Staff Approval และ Vehicle Assignment — 1 นาที 20 วินาที

มี admin role ที่อยู่ใน signed JWT และ backend ป้องกัน admin endpoints ด้วย role middleware. เจ้าหน้าที่ดูคำขอที่รอตรวจ อนุมัติหรือไม่อนุมัติพร้อมเหตุผล และลงทะเบียนรถจริงก่อนเลือกมอบหมาย

การมอบหมายตรวจว่ารถ active ความจุเพียงพอ และไม่มีภารกิจอนุมัติอื่นในช่วงเวลาทับซ้อน โดยทำการตรวจและเปลี่ยนสถานะใน SQLite transaction. ถ้าอนุมัติโดยไม่ระบุรถ ระบบจะไม่แสดงรถที่ไม่มีอยู่จริง

## 6. Sprint 4: Frontend และ Localization — 1 นาที

หน้าเว็บประกอบด้วย Login, Dashboard, New Vehicle Request, My Requests, Request Detail, คู่มือที่ผู้ใช้เลือกเปิดเอง และหน้าตรวจคำขอสำหรับ admin. หน้าเว็บดึงข้อมูลจาก API จริง มี loading, empty, error และ success state

ภาษาไทยเป็นค่าเริ่มต้นและเปลี่ยนเป็น English ได้ทันทีจาก `ไทย | EN`. Layout ยังคงธีมสีน้ำตาลและรองรับหน้าจอเล็ก มี keyboard focus และรองรับ reduced motion

## 7. สาธิต — 2–3 นาที

1. เปิด Dashboard และสลับไทย/อังกฤษให้ดู
2. Login ด้วยบัญชี demo `tan.khanit@live.rmutl.ac.th` / `rmutl1234`
3. เปิดขอใช้รถ เลือกเที่ยวเดียว ระบุเจ็ดยอดไปดอยสะเก็ด วันเวลา จำนวนผู้โดยสารและวัตถุประสงค์
4. ตรวจหน้าสรุป แล้วส่งคำขอ
5. แสดง ticket ผลลัพธ์ว่า “ส่งคำขอสำเร็จ” และสถานะ “รอตรวจสอบ”
6. เปิด My Requests และ Request Detail; ทดลองยกเลิกคำขอที่ยัง PENDING แล้วตรวจว่ารายการยังอยู่ในประวัติ
7. หากสาธิต admin ให้ login `admin@live.rmutl.ac.th` / `rmutl1234` ในฐานข้อมูล disposable. อนุมัติโดยยังไม่ระบุรถได้ หรือบันทึกรถ demo โดยระบุชัดว่าเป็นข้อมูลสาธิต ไม่ใช่ตำแหน่งรถจริง
8. สาธิต guide โดยเลือกเมนูเอง; ไม่มี onboarding popup

## 8. การทดสอบและข้อจำกัด — 1 นาที

ผลตรวจรอบ implementation: backend 50 tests, frontend 15 tests, API checks 4/4, frontend checks 7/7 และ production build ผ่าน. HTTP smoke บนฐานข้อมูล disposable ตรวจ one-way/round-trip, PENDING, owner access, cancellation/history, admin approval/rejection, assignment และ overlap

ยังไม่มี browser click-through E2E หรือ deployment จริง. ทะเบียนรถเริ่มว่างและต้องลงทะเบียน fleet จริงโดย admin. ระบบไม่มี GPS และไม่มี notification service; ผู้ใช้เปิด My Requests เพื่อตรวจสถานะ. ฐานข้อมูล production แบบ persistent ยังไม่ได้ตั้งค่า/ทดสอบ

## 9. สรุป — 30 วินาที

ระบบนี้รับความต้องการใช้รถล่วงหน้าและเก็บคำขอให้ตรวจสอบอย่างมีประวัติ โดยแยกการส่งคำขอออกจากการอนุมัติ เจ้าหน้าที่เป็นผู้พิจารณาผ่าน endpoint ที่ป้องกันด้วย admin role และผู้ใช้ติดตามสถานะได้ทั้งภาษาไทยและอังกฤษ

## Checklist ก่อน demo

- ใช้ database disposable และยืนยันว่า user/admin demo password ใช้ได้
- เตรียมวันเวลาล่วงหน้า; round trip ต้องมีเวลากลับ
- แสดง PENDING โดยไม่เรียกว่าอนุมัติหรือจองสำเร็จ
- ถ้าสาธิต assignment ให้ใช้ข้อมูลรถที่ระบุว่า demo หรือทะเบียน fleet ที่ได้รับอนุญาตจริง
- อย่านำเสนอว่า GPS, notification, production deployment หรือ remote persistence ผ่านการตรวจแล้ว
